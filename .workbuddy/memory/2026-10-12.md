## 排查并修复「摄像头拍照很模糊」

- 定性：原 `camera.py` 只有「相机能不能用」的判定（not_found/unreachable/unknown），**完全没有「拍得好不好」这一层**。糊图照样 base64 喂给 Claude，AI 仍会输出「叶片饱满」之类的结论 —— 属最危险的静默失败。本次同时补上画质可观测性。
- 根因（首要）：**AF 从未被触发**。相机是 Pi Camera v3 = **IMX708（VCM 自动对焦）**，libcamera 不会在 capture 瞬间自动对焦；原流程 `start()` + `sleep(2)` + `capture_file()` 等于盲拍，对焦环可能停在无穷远，拍 0.5~2m 花架必然整幅发虚。全文件搜索确认无 `set_controls`/`autofocus_cycle`/`AfMode`。
- 次要软件根因：① 3A 未收敛（固定 sleep、不读 metadata）；② 未设曝光上限（IMX708 最长 1.72s，清晨拍照必拖影）；③ `1920×1080` 非 IMX708 原生模式（原生仅 4608×2592 / 2304×1296 / 1536×864），ISP 重采样导致偏软；④ 诊断工具只判 `size<20KB`，对「糊」无感知。
- 关键技术发现：**Picamera2 在 `AfMode=Continuous` 下调用 `autofocus_cycle()` 会抛 RuntimeError**（读源码确认）。∴ 静止花架应用 `AfMode=Auto` + 拍照前显式触发，而非 continuous —— 避免了写出必然抛异常的代码。
- 已实施：
  - `hardware/camera.py`：新增 `_wait_for_focus()`（`autofocus_cycle` + 记录 triggered/locked/elapsed/af_state）、`_settle()`（丢 2 帧让 AE/AWB 收敛）、`apply_capture_controls()`（逐个下发 AfMode/AfRange/FrameDurationLimits/AeExposureMode/Sharpness/NoiseReductionMode，单项失败只记 skipped 不中断）、`_save_still()` 改用 `capture_request()` 同帧取元数据（ExposureTime/AnalogueGain/LensPosition/AfState）、`native_mode_hint()` 非原生分辨率告警、`assess_image()` + `judge_quality()` 画质评估与分诊。设计取舍：**对焦失败与画质异常都不阻断拍照**（拍照是浇水/报告流程的一环），只记录 + WARNING + 状态外泄。
  - `config.yaml`：`resolution` 改 `[2304, 1296]`（原生模式、同 16:9 视角）；新增 `autofocus: auto` / `af_range` / `af_wait_sec` / `lens_position` / `max_exposure_us: 66666` / `exposure_mode` / `sharpness_boost` / `jpeg_quality` / `settle_frames` / `quality_guard{min_sharpness:8, min_contrast:12}`。
  - `assistant.py`：新增 `_quality_banner()`，画质告警横幅顶到报告与钉钉消息最前面；`Camera` 构造改传 `capture_settings=cam_cfg`；`status_text()` 展示分辨率提示与上次画质。
  - `tools/camera_diag.py`：`--live` 输出画质指标/对焦过程/拍摄元数据/分诊结论，检查「已生效控件」vs「未生效控件」，`--baseline` 存基线做跨时间对比；退出码新增 **2 = 相机可用但画质异常**。
  - `tests/photoAndAnalyse.py`：拍完直接打印画质指标与建议（现场最直接的验证入口）。
- 清晰度指标标定（本地合成图，纯 PIL 无 numpy/cv2）：清晰 ≈100.1、模糊 0.6px ≈78、1.0px ≈53、1.6px ≈28、2.4px ≈11、4px ≈1.8、纯色 0。默认门槛取 8.0（bad 线 4.8）偏保守，**绝对值与场景强相关**，需现场存基线。
- 发现并修掉两个自身引入/原有缺陷：`parse_capture_settings` 只认 `af_mode` 而 config 写的是 `autofocus`（会导致配置静默失效，被新测试抓到）；`diagnose()` 的 `os.getuid()` 在 Windows 不存在（加 hasattr 兼容 + video 组检查限定 Linux）。
- 验证：`tests/test_camera.py` 23 passed；**全量 73 passed / 0 failed（202s）**；`camera_diag.py` 在 Windows 上正确报 not_found 并给建议（退出码 1）。

## 实现「每日照片 + 报告」的钉钉推送

- 定性（双根因）：① 定时任务一直在跑，但**照片从来没进推送逻辑** —— `take_photo_and_report()` 只发了「已拍摄花园照片: xxx.jpg」的**文件名文本**，`send_image()` 从未被调用；② 更严重的是 `DingTalkBot` 只实现了 webhook 通道，且**无 webhook 时只打一行 mock 日志就返回 `errcode=0`**，调用方以为推成功、用户什么都没收到、日志无报错。
- 关键事实核实（钉钉官方文档）：① 自定义机器人 webhook **不支持** `msgtype:image`（搜索引擎里大量"base64 发图"的博客是错的或讲的企业微信），markdown 图片由**钉钉服务端抓取**、必须公网可访问 URL，本项目家庭内网无公网 IP → 照片永远裂开；② 企业内部机器人 `sampleImageMsg` 的 `photoURL` 官方原文「可填写图片的完整 URL 路径，**也可填写图片的 mediaId**」→ 内网也能发图。这两条决定了整个方案选型。
- 方案：企业内部机器人单聊三跳链路 —— `api.dingtalk.com/v1.0/oauth2/accessToken` → `oapi.dingtalk.com/media/upload?type=image`（拿 `media_id`）→ `api.dingtalk.com/v1.0/robot/oToMessages/batchSend`（header `x-acs-dingtalk-access-token`，`msgKey=sampleImageMsg`）。**不需要公网 IP / 图床 / AgentId**，用已有 `CLIENT_ID/SECRET/ROBOT_CODE` 即可。
- 实测验证（真实凭证、真实网络）：新版 accessToken ✅、旧版 token ✅、图片上传成功拿到 `media_id=@lADPM2Cvo…` ✅ —— 链路完全打通，无需等现场部署。
- userId 来源：钉钉**不允许机器人凭空发起单聊**（否则 `robot.oto.notExist` / `session.notExisted`），故 Stream 收到消息时把 `senderStaffId` 自动写入 `data/subscribers.json`（原子写 + 去重），并提供「订阅」指令。**前提是用户先和机器人说过话**，这是钉钉产品约束而非 bug。
- 改动：
  - 新增 `dingtalk/robot_notifier.py`：双 token 缓存（提前 300s 刷新）、`upload_image()`、`send_image/send_markdown/send_text`、20/批分批、markdown 超长截断、`classify_api_error()` 把钉钉错误码翻译成带 `hint` 的分类（not_configured/no_session/no_permission/unreachable/too_long/…）；`_safe()` 保证任何异常都不会让定时任务崩掉。
  - 新增 `dingtalk/subscribers.py`：`SubscriberStore`（原子写、损坏文件显式报错且**不清空**）。
  - `dingtalk/bot.py`：`DingTalkBot` 改为**多通道路由**（robot → webhook → none）；`none` 时仅 `mock_hardware=true` 允许本地打印，否则返回 `not_configured`。新增「订阅」指令与 `on_sender` 回调。
  - `assistant.py`：`take_photo_and_report` 改为**照片先于报告**（AI 分析要几十秒），照片推送失败把 `⚠️ [推送失败:分类]` 写进报告抬头；新增 `notify_failure()`（定时任务崩了要主动告知用户）、`_push_status_line()`（状态里显示推送通道自检）。

  - `config.yaml`：`dingtalk` 段补 `robot_code_env`/`user_ids`/`subscribers_file`/`image_public_base_url`/`push_timeout_sec`/`max_markdown_chars`；新增 `push` 段。

## AI 分析改为可配置多模型，并消除静默降级（承接上条遗留项）

- 定性（双问题）：① 上条遗留项坐实 —— 取不到 key 时 `PlantAnalyzer` **静默返回写死的假报告**，格式/评分/推送全正常，只有内容是编的；② AI 层硬编码 anthropic SDK，换模型必须改代码。
- **关键事实核实（以实测为主，不信搜索里的 AI 生成博客）**：
  - 用真实 `DEEPSEEK_API_KEY` 实测：官方 API 现模型为 `deepseek-flash`（V4.1-Flash，**支持 text+image**）与 `deepseek-v4-pro`（**仅 text**）；旧名 `deepseek-chat` 仍可用（路由到 flash）。`GET /models` 的 `input_modalities` 可直接判视觉能力。
  - ⚠️ **纯文本模型收到图片不报错**：`deepseek-v4-pro` + 图片 → **HTTP 200**，图片被换成 `[Unsupported Image]` 文字，模型看不到图却照常输出。这是比原问题更隐蔽的静默失败，必须**发送前**拦截。
  - DeepSeek **思考模式默认开启**（effort=high），**不支持 `temperature`**（传了不报错也不生效）；`max_tokens` 太小时 `content=""` 且 `finish_reason="length"`（token 全被思维链吃掉）。关闭方式：OpenAI 格式 `{"thinking":{"type":"disabled"}}`，走通用 `extra_body` 透传。
  - DeepSeek 另有 **Anthropic 兼容端点** `https://api.deepseek.com/anthropic`；`detail:"low"` 可把图缩到 512×512 省 token；图片只能出现在 user 消息中。
  - Claude 模型名核实：`claude-opus-4-7` 真实有效（另有 opus-4-8 / sonnet-4-6 / fable-5 等）。
- 方案：**provider 抽象 + 预设表 + 通用 `extra_body` 透传**，不硬编码任何厂商私有字段。
- 改动：
  - 新增 `ai/errors.py`：`AIError`（kind + hint，与 `hardware/errors.py` 同构），分类含 no_api_key / auth_failed / rate_limited / **vision_unsupported** / model_not_found / unreachable / bad_response / empty_response / **truncated** / invalid_config。
